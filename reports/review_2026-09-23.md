**Personal Jev — project review, 23 September 2026**

The project demonstrates that a useful instruction-conditioned classifier can be assembled and adapted from a public reranker with modest local compute. The central implementation is sound. The evidence supports a substantial improvement from supervised LoRA. Performance parity with Jev remains untested, and several evaluation and reporting defects need correction before publishing a strong comparison.

This review covers the supplied implementation brief, every Python module in src/personal_jev, both test files, all experiment/data scripts, configuration and dependency declarations, README, training metadata and adapter configuration, saved evaluation predictions, calibration files, completed benchmark reports, labeling briefs, and samples of authored data and blind reviews. It does not constitute human verification of every label.

I ran the 35 logic tests: all passed. I inspected the six real-model tests but did not rerun them because the existing GPU benchmark was active. I did not retrain, change implementation/data/weights, or stop the benchmark. This report is the only new project file.

**What is implemented correctly**

The scorer follows the official Qwen Transformers prompt and yes/no scoring pattern, includes template tokens in length checks, left-pads inputs, extracts the final prediction position, and preserves the causal attention behavior. Its supported logits_to_keep=1 path avoids projecting every token through the vocabulary head. Existing real-model tests compare probabilities with the official reference and check batching, order mappings, gradients and fp32 adapter reloads. See [model.py](../src/personal_jev/model.py#L59) and the [official Qwen reference](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B).

Binary sigmoid, per-question multiclass softmax, and independent multilabel sigmoid are appropriate implementations of the chosen v1 design. Request parsing rejects malformed inputs, duplicate IDs and inappropriate thresholds. Overlength inference raises an explicit error.

Training uses BCE for binary/multilabel and grouped cross entropy for multiclass. Whole questions stay together; multilabel loss is averaged within each question, and accumulated gradients are normalized by the optimizer step's question count. LoRA actually updates attention projections; this is not a new classifier head. The recorded pilot has 4,587,520 trainable parameters, 10,112 available training questions, 183 optimizer steps, and the selected checkpoint at step 150. The run took 3,794 seconds including its surrounding evaluation/checkpoint work.

Prompt selection uses validation rows. Temperature fitting uses calibration rows, and threshold selection uses validation rows. CLI calibration loading checks model/revision/adapter-weight hash/prompt identity. Those safeguards are useful, although split-name checks cannot detect shared source content.

**Findings requiring changes**

1. **P1 — Split by the underlying document and template before selecting rows.** [build_hf.py](../scripts/build_hf.py#L182) makes source_id equal to a dataset row index. MNLI contains several hypotheses for the same premise, so row uniqueness does not imply document separation. I found 23 normalized identical-premise groups crossing partitions: 17 validation/test, 5 calibration/test, and 1 validation/calibration. This places 22 final-test questions on passages already present in a selection/calibration partition. I found no exact train/test state overlaps in this scan.

   The authored splitter has the corresponding template problem: [build_data.py](../scripts/build_data.py#L36) hashes each new source_id even when the source is a minimal variation of another. For example, epol-009 is validation and epol-010 is test, but their long policy/case texts differ only in an injury date. Their word-8-gram containment is 98.5%. Six authored cross-split pairs meet a 70% containment diagnostic; these are related policies/cases, not six proven label leaks. Also, the development fixture dev-001 has the exact state used by test source erout-001, which contributes three test questions.

   Use canonical source groups and explicit template/augmentation parent IDs across every partition, including dev; assert disjointness before training, calibration and comparison. Preserve existing results as exploratory. Build a fresh frozen test for subsequent model selection. This defect does not explain away the improvement: excluding the 22 affected MNLI test rows leaves 278 rows, with accuracy 57.6% baseline versus 88.8% LoRA.

2. **P2 — The pilot reload check does not enforce reproducibility.** [train.py](../src/personal_jev/train.py#L245) calculates a score discrepancy and records it, but never rejects an excessive difference. The actual [pilot metadata](../runs/lora_pilot/train_meta.json#L293) records a maximum absolute score difference of 0.125. The fp32 smoke tests use a 0.001 tolerance. Different precision warrants an explicitly justified tolerance; it does not justify describing every reload as giving the same scores.

   Establish a bf16-specific acceptance criterion, record effective base and adapter dtypes, preserve the exact reference batch, and measure probability/decision changes after reload. Fail or mark the run unverified when it exceeds the criterion. The saved, reloaded adapter was evaluated in fp32, so this finding does not invalidate those saved test predictions.

3. **P2 — Aggregate label metrics merge IDs belonging to different tasks.** [evaluate.py](../src/personal_jev/evaluate.py#L105) computes multiclass macro-F1 from bare label IDs across all datasets and dynamic questions. Its multilabel per-label accumulation does the same at line 118. IDs such as none, positive or neutral are local identifiers and are not guaranteed to define a single global class.

   At minimum namespace by dataset/task and label; dynamic taxonomies need an explicit label-space identity. Prefer a clearly specified average of per-task metrics. Merely adding the family namespace changes baseline multiclass macro-F1 from 79.6% to 78.6%, and LoRA from 82.3% to 81.6%. Accuracy is unaffected.

4. **P2 — Paraphrase consistency incorrectly depends on multilabel list order.** [evaluate.py](../src/personal_jev/evaluate.py#L167) serializes selected lists directly; sort_keys sorts dictionary keys, not list elements. The LoRA predictions for emul-019-q1 and emul-019-q2 contain the same four label IDs in different orders, yet count as inconsistent.

   Normalize multilabel selections as sets/sorted IDs. Correcting this calculation gives LoRA consistency of 6/11 = 54.5%, versus the reported 5/11 = 45.5%. Baseline stays 8/11 = 72.7%. The remaining inconsistency is real; the all-correct metric is unaffected.

5. **P2 — Benchmark precision and quality are not paired.** Both saved baseline and LoRA quality reports use fp32. The completed bf16 speed report evaluates the unmodified baseline only. [run_experiments.sh](../scripts/run_experiments.sh#L31) schedules baseline fp32, baseline bf16 and LoRA fp32, with no LoRA bf16 quality/latency comparison.

   Before claiming a deployable quality/speed point, evaluate the exact serving model, precision, adapter and batching configuration together. This matters especially because the training code itself notes bf16 score sensitivity to batch composition.

**What the results establish**

I independently recalculated all headline metrics from the saved raw and calibrated test predictions; they match the four report JSON files. The two raw reports use the same IDs and targets. Their data-file hashes match the current files, and the recorded adapter hash matches the saved weights. The blind review files contain 398 answers, all matching the authored targets; the inspected blind inputs exclude targets and author notes. That is verified model agreement, not independent human ground truth.

| Test slice | Questions | Baseline accuracy | LoRA accuracy |
|---|---:|---:|---:|
| Entire mixture | 3,471 | 61.0% | 73.5% |
| Public datasets represented in adaptation training | 1,500 | 55.5% | 73.5% |
| Public datasets excluded from adaptation training | 1,800 | 67.7% | 75.3% |
| Newly authored diagnostic questions | 171 | 39.2% | 55.0% |

The 12.5-point overall gain is substantive. A diagnostic bootstrap that resamples normalized source states, keeping their questions together, gives a 95% percentile interval of approximately +11.0 to +14.0 percentage points over 2,000 resamples, seed 23. For the authored set, 171 questions reduce to 66 distinct state clusters, and the gain interval is approximately +7.5 to +23.5 points. These intervals do not repair split contamination, account for every shared template, or establish performance on an unknown deployment distribution.

The original question-level McNemar test treats related questions as independent pairs. Use clustered uncertainty estimates for authored data, and account for multiple comparisons before declaring individual families improved. The broad improvement survives this more careful view.

**How to interpret the benchmarks and weak spots**

The public datasets are custom reformulations, not their standard benchmarks:

| Dataset-derived task | Candidate set actually tested |
|---|---|
| Banking77 | Gold plus 7 random negatives: 8 options |
| CLINC | Gold plus 6 random negatives plus none: 8 options; 7 for out-of-scope rows |
| DBpedia-14 | Gold plus 5 random negatives: 6 options |
| GoEmotions | All annotated positives plus sampled negatives: 6 labels in every test row |

These are legitimate dynamic-candidate experiments, but the dataset names alone make them look like harder full-label benchmarks. Label them explicitly. Random negatives also underrepresent confusing alternatives, and GoEmotions' construction changes label prevalence and omits the usual full taxonomy. See [build_hf.py](../scripts/build_hf.py#L100).

The six held-out public datasets are excluded from this adaptation's training. They do not all represent unseen kinds of reasoning: sentiment, intent and emotion are already represented elsewhere in the training mixture. Pretraining exposure is unknown. The agent-output family is excluded from gradient training, but its validation questions influence prompt/checkpoint selection, so describe that distinction.

The task-specific gaps are substantial: LoRA gets 12/26 agent-output questions and 9/22 policy questions right. Across all authored multilabel questions, exact match is only 10/44 = 22.7%. Those estimates are noisy, but sufficient to show the current limits.

A concrete saved failure: the state says Pellmont owes our company money. The question asks whether our company owes Pellmont. LoRA returns true with p_yes = 0.9886. See [saved prediction](lora_pilot/test/report.json#L117417). The numeric comparison of 8,412 with 8,500 also fails. These examples illustrate why typed output alone does not ensure factual correctness.

The impressive contradiction and missing-evidence slices largely measure MNLI: respectively 94/107 and 97/104 questions come from that training-represented family. Report authored and unseen-dataset slices separately before generalizing these gains to arbitrary reasoning.

Aggregate binary ECE of 0.066 hides variability. For example, raw LoRA binary ECE is approximately 0.189 on SST-2 and 0.500 on the tiny policy slice; calibrated policy ECE remains approximately 0.482. Small slices make ECE unstable, but the high-probability failures still require domain-specific validation. Temperature scaling is a conventional useful baseline, not evidence of an independent uncertainty mechanism.

**What this says about reproducing Jev**

Typed classification without text generation is demonstrably accessible. The wrapper, loss functions and post-processing do not require a new research breakthrough. This experiment gives useful evidence that ordinary supervised adaptation can improve a small pretrained reranker locally.

Jev's broader public claim combines decision quality, calibration, latency and weak latency growth with extra questions. Its documentation says questions run independently and in parallel, with little extra response time. Your implementation repeats the document for every candidate; 16 three-way questions create 48 document encodings, and measured latency grows roughly with that work. That is an observed limitation of this implementation, not proof about Jev's hidden internals. See [TypeSafe introduction](https://docs.typesafe.ai/introduction) and its [launch claims](https://typesafe.ai/blog/introducing-system-one-models-and-jev).

A useful clarification from the current docs: Jev's confidence field is described as a statistic of its probability distribution. There is no public basis here for insisting that a separate confidence head must be recreated. See [TypeSafe confidence](https://docs.typesafe.ai/confidence).

The independent candidate design also limits candidate-set-dependent semantics: a generic none-of-the-above candidate never sees the other candidates. Argmax may still choose it appropriately from relative scores, but the none score itself cannot reason over which other options were supplied. The selected architecture also lacks rubric scoring, deliberately deferred in the brief.

No direct Jev comparison has been run. A hosted service's latency and a local MPS benchmark are different hardware/serving conditions; these measurements establish neither architectural superiority nor impossibility of closing the gap. TypeSafe's advertised results likewise do not substitute for an independently checked comparison.

**Recommended next work**

First fix source/template grouping, the two metric defects, and reload acceptance. Freeze the current run, including code version, data and adapter artifacts; the current gitignore excludes weights and raw prediction JSON, so a public release needs a deliberate artifact retention/distribution plan.

Then create a fresh human-reviewed test reflecting intended tasks: rules, role reversals, negation, unseen instructions, difficult competing candidates, zero-positive multilabel cases, and meaningful long-context evidence positions. Keep existing test data out of future selection. Report accuracy, Brier/log loss, coverage versus accepted error, and intervals by task.

Next establish one paired quality/latency result for the intended serving configuration, including the tuned model in bf16 if that is the speed target. Optimize only against that measured baseline.

Finally, with access to Jev, run the identical frozen states/questions/candidates through both systems, alongside a strong conventional reference. Compare quality and calibration at the same task definition, report end-to-end latency/cost and hardware conditions, and avoid selecting examples after seeing outputs.

The defensible claim today is: “We built a compact open classifier around Qwen3-Reranker and substantially improved its typed decisions with roughly an hour of local supervised LoRA adaptation.” Matching Jev's advertised quality/latency/calibration combination remains an experiment to perform.
