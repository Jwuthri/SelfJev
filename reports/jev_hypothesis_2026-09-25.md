## 2. What that implies (inference, not fact)

1. **Layout: a shared state with isolated per-question branches.** The limit "state plus the longest question" means
   each question is scored as `state + that question`, never `state + all questions`. That is our tree.
2. **Options inline, one readout per option: the "parallel sampler".** 113 billed tokens per 3-option question is
   the question, its option list and a few tokens per option; the question is billed once, not once per option.
   Our evidence points the same way: listing the options helps (+1.2 on top of round 3), and option pointers lost
   0.9 only because the readout position no longer held the option's text.
3. **Small model on fast hardware.** 400K tokens/s marginal for one request, at 2 FLOPs per parameter per token and
   about half of peak, is ≈ 0.6B dense parameters per H100 or ≈ 1.4B per B200, twice that in FP8, more with tensor
   parallelism. So a model of at most a few billion parameters (or an MoE with that many active), not a trick that
   skips tokens. The 113–136 ms floor at 8 tokens is a network hop plus a batching queue, not compute, and the p95
   says the same: their model is a small part of their latency. **Confirmed on 2026-09-26:** the same 4B tree on one
   H100 is faster than Jev inside the machine at every request size (server-side 22–82 ms vs 110–122 ms, one question);
   Jev's per-token cost stays ≈ 6× lower, so it is smaller or spread over more GPUs, but the flat curve is hardware.
4. **Trained on frontier-model judgments, not on public human labels.** On the dev benchmark Jev scores 82.7 like
   every 4B of ours, and its multilabel exact match there is 40.1 against our 57.6: it never learned GoEmotions- or
   TweetEval-style conventions. Its reference answers are frontier averages, and eval2 keeps only questions where two
   frontier judges agree with the author, so **97.2 also measures agreement with the judges that built eval2**. Our
   training data uses the same judge (Astra), so we are aligned to the same signal, with fewer examples.
5. **RLCD = a calibration objective.** Its errors are hedged (34 of 55 with margin < 0.2, 7 confidently wrong), and it
   is more graded than we are. That is what a proper-scoring-rule reward produces. Ours are trained with hard
   cross-entropy and are confidently wrong 4× as often per error.
6. **No hidden reasoning.** Its weakest slices are numbers and dates, exactly where a single forward pass without
   chain of thought fails; ours are weakest there too.
7. **Tokenizer:** not Qwen's (1.036×); probably a 100K+ BPE vocabulary, a small wordpiece vocabulary would cost more.
8. **"Not an LLM" / "new architecture"** most plausibly means: no generation head, the branch layout, per-option
   readouts and a calibrated decision head. Nothing measured requires a from-scratch backbone.

## 3. What our failures already rule out

| tried | eval2 | lesson |
|---|---|---|
| new cross-attention blocks on a shared encoding (custom model) | 39.0 / 58.2 on the dev benchmark | text and question must meet in every layer, in a pretrained stack |
| T5Gemma 2 encoder–decoder with shared memory | 73.0 / 76.8 | a pretrained reader in a new input layout does not carry over |
| jina 0.6B listwise | 73.3 | sub-1B with our data volume is 17 points behind |
| Qwen 0.6B tree | 68.8 | same |
| option pointers | −0.9 | the readout must sit on the option's text |

So the quality is the pretrained LM's deep joint reading plus its own yes/no readout, adapted with verified data.
A from-scratch Jev would need frontier-labelled data far beyond our rounds (≈ $280 for 38.6K verified questions).
The new architecture should change the **readout, the objective and the serving**, not the backbone.

## 4. Proposals, ranked

### A. Parallel-readout branch (the closest thing to Jev's "parallel sampler")

One branch per question instead of one leaf per option: the question, then every option listed, then a short
verdict block with one readout position per option and one for `none`:

```
[instructions + state] ── [question + "Options:\n- A …\n- B …\n- C …" + "\nVerdicts:\nA:" ⟶ z_yes−z_no (A)
                                                                        "\nB:"            ⟶ z_yes−z_no (B)
                                                                        "\nC:"            ⟶ z_yes−z_no (C)
                                                                        "\nnone:"         ⟶ z_yes−z_no (reject)]
```

- Every readout sees the state, the question and the whole option list (the option-list gain), and sits after the
  option's own text (what pointers lost).
- Multiclass = softmax over the option readouts (+ `none` when offered), trained listwise; multilabel = per-readout
  sigmoid; binary = one readout. The `none` readout is the permutation-invariant rejection rule from the open ideas.
- Cost per question: question + list + ≈ 3 tokens per option, once, instead of n × (question + list + option).
  On vLLM that is 16 prompts for 16 questions × 8 options instead of 128, which is where pointers failed.
- Trade-off: readouts share one causal context, so option order can change scores (Jev has the same property, we
  test it with permutations); the exact per-pair semantics of the current tree is lost.
- Code: tree encoding with several readout positions per leaf, `grouped_loss` over them, eval and serve paths
  (transformers first; vLLM needs per-token pooling or prompt logprobs at the readout positions).
- Gate: ≥ the best single model (`qwen35_4b_tree`, 95.6) on eval2 with fewer branch tokens, multilabel EM up. Cost ≈ $12 (g5.xlarge, the
  round-3 mix), less if the branches are shorter.

### B. A calibration objective in the same run (RLCD without the RL)

Add a proper-scoring term (Brier) and mild label smoothing / soft targets from the two judges where they exist,
and report graded-probability share, confidently-wrong count and ECE next to accuracy. For a differentiable
decision head, maximising a proper-scoring-rule reward is minimising that loss directly. This is what turns
Jev's errors into hedges, and it is what makes proposal C work better. Cost: none beyond A, plus one A/B run
(≈ $12) if A wins.

### C. A cascade or ensemble in serving, today ($0 to decide)

From [eval2/ensembles.md](eval2/ensembles.md), nothing fitted:

- We are unsure on most of what we lose (see the end of ensembles.md: most of the questions Jev wins have our margin
  below 0.4).
- Deferring to the 27B **alone** does not help beyond a few percent deferred; averaging does. A stronger fallback (a frontier model on
  10% of the traffic) would recover most of the gap, at that model's latency on those questions.
- The threshold must be chosen on validation: `reports/teacher/qwen38_27b_validation.jsonl` and the tree's
  validation predictions exist, so this is a $0 decision.

### D. Measure the speed gap on the right hardware before redesigning for speed

The A10G is compute-bound at 6.5–10K tokens/s. An H100 in FP8 is 15–20× that, so a 4B tree at 4K tokens × 16
questions should land near 100 ms server-side (an estimate to verify, not a result). **AWS only** (the user's
rule, 2026-09-26: no RunPod). On 2026-09-24 every p5.4xlarge (1× H100 80 GB) launch failed for capacity. On
2026-09-26 the free signals are better: the account's P-instance quota is 768 vCPUs (us-east-1/us-west-2) and 384
(us-east-2); the spot placement score for p5.4xlarge is 9/10 in us-east-2 (1/10 elsewhere), and 9/10 for
g7e.4xlarge (1× RTX PRO 6000 Blackwell, 96 GB, $4.00/h on demand) in us-east-1; spot p5.4xlarge trades at ≈ $2.63/h,
on demand ≈ $6.88/h. Only a launch confirms capacity; a failed launch costs nothing. Plan: spot or on-demand
p5.4xlarge in us-east-2 with no AZ pinned, then g7e.4xlarge in us-east-1; the existing sweep
(`scripts/latency_sweep.py`) with `tree_4b_combo` merged on vLLM, bf16 then `--quantization fp8`, plus an eval2 check
of the FP8 path; ≈ 1.5–2 h ≈ $5 spot / ≈ $12 on demand. If no launch succeeds, D stops. It should run before any
speed-driven architecture work.

**Result (2026-09-26, p5.4xlarge spot in us-east-2, ≈ $2.54/h):** the speed gap was hardware. Server-side the H100
answers in 22–82 ms for one question and 58–189 ms for 16 (Jev 110–134 ms); end to end we trail by 10–100 ms, which
is the 61 ms network hop against OpenRouter's 11 ms. FP8 adds nothing. Table and details:
[docs/speed.md](../docs/speed.md#the-same-model-on-an-h100-2026-09-26). No speed-driven architecture work is needed;
proposals A–C and E are about accuracy.

### E. Bidirectional state, causal branches (prefix-LM), a pilot

In the tree the state is read causally: a token never sees what follows it, so an exception or a date at the end
of the state cannot reshape the representation of the rule at the start; only the branch can reconcile them.
A full attention mask over the state with causal branches (PaliGemma-style prefix attention) fixes that at no
extra cost; decoders adapt to it with light fine-tuning (LLM2Vec). Unknowns: whether the reasoning slices move
(long-state slices are already 95–99), and serving (vLLM has no prefix-LM mask for decoders; transformers or
FlexAttention do). One LoRA run ≈ $5 on the round-2b mix, after A.

### Not recommended

- A from-scratch backbone or new heads on frozen encodings (section 3).
- A sub-1B student now: 17 points behind with our data; revisit only with A's soft targets and D's numbers.
