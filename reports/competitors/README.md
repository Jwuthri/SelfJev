# Open Jev-like models vs selfjev-4b-vision, same GPU, same requests (2026-09-30)

Session "Claude competitors". Survey and shortlist: [docs/landscape.md](../../docs/landscape.md#the-open-field-and-the-shared-yardsticks-survey-2026-09-30).

## What was run

One AWS g6e.xlarge (L40S 48 GB, 4 vCPU, 30 GB RAM), us-east-2, `i-0d7e62883fb38d56a`. Each competitor was installed in
its own venv from its card's recommended recipe (`scripts/eval/competitors/setup_<name>.sh`, pinned revisions), served on
its own `/v1/systemone` server, scored, then killed (`scripts/eval/competitors/queue.sh`, `lib.sh`, `jobs/`).

| column | data | harness | how a question is asked |
|---|---|---|---|
| eval2, eval_llm, image test | our frozen test files `data/eval2.jsonl`, `data/eval_llm.jsonl`, `data/eval_images_v1.jsonl` | `scripts/eval/score_systemone.py` + our evaluator | exactly Jev's request (`compare_external.py` mapping): binary -> noul, multiclass -> choice over the candidate descriptions, multilabel -> one noul per candidate; one request per text. A failed request counts as wrong |
| typed-decisions | LocalLLaMA/typed-decisions test, 400 cases x 5 questions | `scripts/eval/score_typed_decisions.py` | the dataset's own body, one request per case; argmax vs gold `label` |
| JevBench public-231 | fstandhartinger/jevbench @ `bb05a33`, datasets/public | the official runner, `typesafe` adapter | one question per request; per-tier accuracy from `summarize()` (`jb_tiers.py`) |
| Nimble 13 macro | the 13 public subsets (3,880), rebuilt by lev's `s1bench export` @ `0ea955f` | levbench (`s1_levbench_macro.py`) | one request per item |

Our model is served by `selfjev serve` (TreeServer, `weights/selfjev_4b_vision`), which applies the option-list transform
to every request, as in production. Through Jev's request mapping it scores **below its native evaluation** on our sets
(eval2 94.7 vs 96.1, eval_llm 90.7 vs 92.5): the loss is multilabel (86.1 vs 90.8 on eval2), where one noul per candidate
replaces our native `multi` question. The matrix uses the Jev-mapped number, the one every competitor and Jev itself got.

## Caveats per model

- **Laya**: the default English checkpoint reads 512 tokens (the state is truncated); `laya-long` sends `max_len` 8192 and
  `head_max_len` 2048. Server limits (50,000 characters, 512 options per request) were raised so requests are answered,
  not refused.
- **Mica**: llama.cpp b11010 built from source for sm_89; refuses prompts over 8,192 tokens (47 eval2 and 7 eval_llm
  questions unanswered, counted wrong).
- **Plumb**: `jevk5-serve`, plain probabilities at T = 2.07 (no JevBench-v1.5 transform), one question per request (no
  prefix sharing; a > 16-option question fails its request). Its card says the public JevBench aggregate informed its recipe.
- **jpt-4b**: vLLM 0.30.0 + llm2jev 0.6.1, images as chat messages. CC-BY-NC-4.0. Its card says typed-decisions is in
  distribution (trained on its train split), so its 78.8 there is not zero-shot.
- **imajev-4b**: repo `8501f5c3`, torch backend, `--fast --merge-lora`, 1 rotation + calibration (its Image JevBench #1
  configuration); 8 questions per request; `--max-input-tokens 20000`.
- **openjev-27b-fp8**: openjev/openjev-FP8 on vLLM 0.29.0 + the card's shim with its measured readout settings; images as
  `{"image": url}`. vLLM used Marlin weight-only FP8 on the L40S. CC-BY-NC-4.0.
- **Image test**: 6 of its 10 datasets are in selfjev-4b-vision's training data (in distribution for us only); the 4
  held-out datasets (hurricane, indoor, painting, snacks; 772 questions) are the fair image comparison.
- **Speed column**: wall seconds for eval2 (1,991 questions, 647 texts) with 4 requests in flight on the one L40S, end to
  end through each server; not a controlled latency benchmark (servers differ in batching, prefix reuse and chunking).
- Nothing was fitted on any of these sets; no model was trained here.

## DecisionBench: stopped twice, no comparable result

`decision-bench run-system-one-http` (Hanno-Labs/decision-bench @ `9a6328e`, 23,900 rows, max 255 candidates) for
selfjev-4b-vision only.

1. **First try (old code)**, stopped at 2,925 rows: throughput fell from ≈ 250 to ≈ 11 rows/min; `py-spy` showed the
   server CPU-bound in tokenization (`qwen35.py` `entry()` re-tokenized the question, which carries the whole option
   list, once per candidate: quadratic) with the GPU idle. Rows: `decisionbench/selfjev-4b-vision_stopped_2026-09-30/`.
2. **Fix** (same day): the instruction is tokenized once (`head + tokens(" " + answer + tail)`; ":" always ends a
   pre-token, so the ids are identical: 0 mismatches on 54,681 real questions, test
   `tests/engine/test_qwen35.py::test_entry_branches_equal_full_string_tokenization`), and `split_branches` finds the
   shared prefix with `os.path.commonprefix`. CPU time of entry + split for one question: 4 options 0.7 -> 0.3 ms, 64
   options 82.8 -> 4.2 ms, 255 options 1,414.6 -> 28.0 ms (50x).
3. **Second try (fixed code, g6e.2xlarge)**, stopped at 3,460 rows after 51 min: the GPU was now at 100 % (the fix
   works), but the remaining many-option tasks (`route` 2,222 rows x 113 options on average, `tool_route` 2,222 x 64,
   `canonical_entity` 1,600 x 60) run at ≈ 21 rows/min in our tree engine: ≈ 7 h more on an L40S, beyond the approved
   budget. Same answer as the first try on 2,903 / 2,906 shared rows (batch-composition numerics, max |Δp| 0.05).
   65 / 637 `canonical_entity` rows exceed our 32,768-token limit (the option list is in the question and in every
   leaf). Rows: `decisionbench/selfjev-4b-vision_partial_v2/raw.jsonl` (the runner resumes from them).

Per-task accuracy on the finished tasks (errors count as wrong; not a DecisionBench score): bounded_value 93.4
(2,223 rows), agent-readiness-assessment 91.0, agent-result-retention 86.0, browser-action-selection 80.0,
agent-call-retention 78.0, agent-skill-ranking 69.0, browser-target-selection 49.0 (100 rows each), canonical_entity
89.8 (637 of 2,222).
